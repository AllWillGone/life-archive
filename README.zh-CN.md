# LifeArchive

[English](README.md) | 简体中文

让经历有处保存，让回顾有据可查，让下一次对话能够接上之前的自己。当前规则版本：**4.2.0**。

LifeArchive 是用于维护私人记忆库的公开模板，可以长期记录经历、关系、情绪变化和未解决线索。它把可观察事件、使用者的感受与理解、导航摘要和用户原话分层保存，让 AI assistant 能按需恢复上下文，而不是把一生压缩成单一人物画像。

你可以把它理解为一份由自己持有、可以持续补充的个人经历档案：平时自然地与 AI 聊天，由具备文件读写能力的 assistant 按规则整理；以后再聊到同一个人、同一件事或同一种困扰时，能够找到此前的记录，接着理解和讨论。自己也可以直接阅读、搜索和修改这些 Markdown 文件。

本仓库只包含可复用的规则与审计工具、空结构、模板、合成示例和经过清理的研究记录，不得包含任何人的真实记忆库或其 Git 历史。

## 为什么做这个项目

很多有意义的个人信息最初只是聊天里的一句话：一次见面为什么重要，一个决定是怎样作出的，某段时间为什么难受，后来又怎样改变。对话积累后，这些线索会散落在不同日期和不同聊天里；重新开启对话时，往往又要从头交代背景。

只保留一份不断压缩的个人简介，也难以留下这些变化。比如，“我不喜欢公开表达”无法说明当时发生过什么、在哪些场景里紧张、有没有例外，以及后来的感受是否已经不同。LifeArchive 希望保留这些具体经历和时间脉络，让后续理解能回到记录本身。

这个项目的目标，是让个人经历能够长期积累、方便找回，并在后续交流中继续发挥作用。它为 AI 提供可读取的外部上下文，也为使用者留下可以亲自核对的生活档案。

## 能用它做什么

| 使用场景 | 可以怎样使用 | 记录带来的作用 |
| --- | --- | --- |
| 接续长期对话 | 隔了一段时间，再谈某个人、某件事或一个持续中的困扰 | 先恢复近期状态，再查相关经历，减少反复从头介绍背景 |
| 回顾重要经历 | 回看一段学习、工作、搬家、旅行或关系阶段 | 把多次对话里的连续进展放回事件，理解起因、经过和结果 |
| 理解感受变化 | 询问“我当时为什么在意这件事，后来又有什么变化？” | 保留不同时间的感受和理解，避免只剩最后一次表态 |
| 梳理关系脉络 | 查找与同一个人的相处、联系变化和自己的态度 | 用人物入口串联相关事件，区分实际互动与自己当时的猜测 |
| 回看目标与决定 | 找回“我为什么开始”“当时顾虑什么”“后来是否有进展” | 留下本人表达的愿望、决定和实际行动，帮助后续复盘 |
| 准备阶段性回顾或自传素材 | 按时间、人物或主题寻找过去的片段 | 从摘要进入具体记录，必要时核对用户原话，为写作提供材料 |

这些用途依赖实际留下的内容。没有记录的经历不能被凭空补齐，愿望也不能被当成已经完成的行动。对关系和反复出现的感受，档案可以提供讨论依据；他人的真实动机、心理诊断或未来结果不能仅靠记录确定。

## 日常如何使用

1. **准备私人副本。** 按[安全开始](#安全开始)建立自己的目录，让能够读写文件的 AI assistant 读取 `AGENTS.md`。不必先写完个人传记，也不必一次填满所有目录，可以从眼下的一件事开始。
2. **像平常一样聊天。** 讲最近发生的事、旧回忆、矛盾和感受即可。规则要求 assistant 先回应对话本身，再安静完成必要记录；无需把每句话自行拆成字段或填写表格。
3. **让相关内容逐渐连起来。** 普通自传式对话的原话保存在 `session/`；新的事件经过和感受变化分别整理到对应文件。属于同一事件的后续可以持续补充，摘要和索引只在有必要时更新。
4. **下次从已有背景接着聊。** 在新对话中使用[启动提示词](#新对话启动提示词)，让 assistant 先读近期状态、长期总览和索引，再按话题读取相关底层文件。更换 assistant 时，也需要让新工具读取这些文件和规则。
5. **按需要回顾与核对。** 可以问“这件事之前是怎么发展的？”“我当时具体怎么说的？”；发现漏记或误解时，核对来源后修正。积累较多后，可使用[周期整理提示词](#周期整理提示词)先查看整理提议，再决定是否执行。

日常记录依靠你使用的 assistant 执行这些规则。模板本身不会在后台监听聊天、定时抓取其他平台，或自动把档案同步给所有 AI；`maintenance/` 的审计也需要明确启动。基本记录使用 Markdown 文件，周期审计工具另需 Node.js。

## 一个从聊天到记忆的例子

以下内容完全虚构，只用于说明分层方式。假设你在聊天中说：

> 这周去上了第一次陶艺课，做的杯子塌了，有点挫败。但做东西的时候很投入，我想下周再去。

这段话可以在回应之后按不同职责保存：

| 保存位置 | 应保留的内容 |
| --- | --- |
| `session/` | 这条用户消息的全文，保留原本措辞和消息边界 |
| `fact/events/` | 本周参加第一次陶艺课、制作的杯子塌了；没有说出的具体日期不自行补全 |
| `feeling/by_event/` | 有点挫败，同时觉得制作过程很投入，并表达下周再去的愿望 |
| `summary/current.md` | 若这成为持续中的安排，简短保留当前意愿和事件入口，不复制整个过程，也不把“想去”写成“已经去了” |

以后问“我之前为什么想继续学陶艺？”，assistant 就可以沿索引查到那次经历和感受，需要时再核对原话。如果后来兴趣下降，也应按时间补充新的感受，保留前后的变化。

仓库另提供一组可直接查看的合成材料：[学习事件](examples/fact/events/2026-01-example-learning-project.md)、[对应感受](examples/feeling/by_event/2026-01-example-learning-project.md)和[简短总览](examples/summary/overview.md)。它们展示的是文件如何相互关联，不是需要照搬到私人档案中的个人经历。

## 核心模型

- `fact/` 记录发生了什么，并保留来源和不确定性。
- `feeling/` 记录使用者如何感受、理解、反应和变化。
- `summary/`、索引和 `people/` 是轻量路由层，不是底层记录的重复副本。
- `session/` 按日期和发言顺序保存普通自传式对话中的用户消息全文，保留原始措辞、段落和消息边界，供核对、补记和重新整理使用；不生成记忆更新摘要，也不保存 agent 回复、建议、分析或文件清单。旧版摘要保留原样。
- `inbox/` 是无法安全归档内容的最后缓冲，不是主要记录线索。
- `experiments/` 保存系统研究，不属于自传式记忆。

底层原则很简单：忠实保留使用者的记忆，不把它改写得更整洁、更体面或比来源所支持的程度更加确定。

## 为什么这样组织

**按事件串联，按日期保留原话。** 一件事可能在很多天里反复谈到。事件文件把它的连续进展放在一起，便于回顾；按日期保存的原话则提供核对入口。两者分工，可以同时保留“事情怎么发展”和“当时具体怎么说”。

**让事实和感受各有位置。** 同一次经历可以有多种甚至矛盾的感受，事后理解也可能改变。分别保存，能让“发生了什么”和“我如何理解”相互参照，同时保留“我猜”“对方说”等来源限定，减少将推测写成定论的机会。

**让摘要负责找到细节。** `current` 保存仍影响当下的状态，`overview` 保存相对稳定的背景；人物、主题和时间线提供不同检索入口。新对话先读这些入口，具体问题再查相关记录，避免每次载入全部档案。摘要可以调整，但不能成为替代底层经历的唯一版本。

**让记录由使用者持有。** 内容保存在可以直接查看的 Markdown 文件中，可以自行搜索、备份或迁移到其他工具。更换模型后仍可通过文件重新建立上下文，实际理解和执行效果取决于新 assistant 的能力与规则遵循情况。

**让 AI 的理解能够被核对。** 原话、事件、感受和摘要之间保留入口，便于发现遗漏、误归属或过度概括。assistant 自己提出的安慰、建议和分析留在聊天中；只有使用者后来表达的愿望、决定、行动或结果，才作为本人的新内容记录。

## 仓库结构

```text
LifeArchive/
  AGENTS.md                 # 权威维护规则
  README.md                 # 英文项目指南
  README.zh-CN.md           # 简体中文项目指南
  CHANGELOG.md              # 公开模板版本记录
  docs/
    templates/              # 空白记忆文件模板
    public-template-safety.md
    public-template-safety.zh-CN.md
  examples/                 # 只放合成示例
  experiments/              # 系统设计观察与实验
  maintenance/              # 通用审计协议；生成状态保持私有
  summary/                  # 总览、当前状态、时间线、人物、主题
  people/                   # 可选人物路由卡片
  fact/
    index.md
    events/                 # 按事件记录的事实
  feeling/
    index.md
    by_event/               # 与事件关联的情绪记录
  session/                  # 按日期保存用户原话，保留消息边界
  inbox/                    # 未解决碎片
  archive/                  # 仅保存旧格式和迁移备份
```

普通对话从当前状态和索引开始，再按需打开相关底层文件；不会默认读取全部事件、人物卡或实验。完整读写规则见 `AGENTS.md`。

普通自传式对话不读取 `experiments/` 或 `maintenance/`。项目维护、规则讨论、系统实验和周期审计的技术内容不写入自传式记忆目录；使用者明确说本轮不记录时，也不保存原话或另写事实、情绪和摘要。只有使用者明确提出开展或继续系统实验时才读取 `experiments/`；只有明确提出启动、恢复或执行周期审计时才读取 `maintenance/`。

## 安全开始

不要直接在仍连接本公开仓库的 clone 或 fork 中填写私人记忆。填充后的仓库可能通过正文、文件名和 Git 历史暴露姓名、地点、关系和情绪记录。

1. 下载压缩包，或只复制模板中已跟踪的文件而不复制公开仓库的 `.git/` 目录，将它们放入新的私人目录或私有仓库。如果使用 Git，写入个人内容前应确认仓库可见性并运行 `git remote -v` 检查远端。
2. 只向 AI assistant 授予该私人目录的读写权限，并让它先读取根目录的 `AGENTS.md`。
3. 决定是否用 Git 版本化私人记忆。附带的 `.gitignore` 会忽略部分新建底层记录，作为有限的纵深防护；只有确认仓库为私有后，才按需要删除或调整这些规则。
4. 人工审阅重要写入，并根据内容敏感程度维护加密备份。

`.gitignore` 不是隐私边界。已经被 Git 跟踪的初始摘要和索引在填入内容后仍可被提交；私有仓库本身也不等于加密。首次使用或公开发布前，请阅读[公开模板安全说明](docs/public-template-safety.zh-CN.md)。

## 周期审计

公开模板包含通用 maintenance-5 审计引擎，供复制到私有仓库后使用。它采用“轻量审计、严格执行”模式：可以审计一篇、多篇、全部已变化文档或完整配置范围；只显示带有精确修改前后的真实建议，不铺开每份已审计文档；每项修改始终由使用者决定。

新建私有副本后先初始化一次本地基线：

```text
node maintenance/.system/audit.mjs init
```

然后使用下面的周期整理提示词。命令拒绝替换已有状态。请把 `maintenance/baseline.json`、`maintenance/run/`、`maintenance/proposal.json`、`maintenance/proposal.md`、`maintenance/proposals/`、`maintenance/reviews/`、迁移备份、锁和恢复材料保持私有，不要提交到公开仓库。

范围选择、精确审阅、自定义提议、授权和恢复流程见 [`maintenance/README.zh-CN.md`](maintenance/README.zh-CN.md)。

## 新对话启动提示词

适合普通对话。提示词只引用 `AGENTS.md`，避免复制一份会随版本漂移的规则正文。

```text
请先读取当前仓库根目录的 AGENTS.md，并按其中“启动上下文构建”和“按需深入与写入前读取”规则建立上下文，不要默认读取全部底层记忆。

之后像平常一样优先和我聊天、分析和回应，不要把自己变成记录员。按 AGENTS.md 安静将我的原话追加到 session；出现新的事实、情绪变化、关系线索或事件线索时，再维护对应的事件和必要索引。项目维护和我明确不记录的内容不保存。
```

## 周期整理提示词

适合索引、摘要、事件边界或待处理内容逐渐漂移时使用。它要求先审计，再进行任何重构。

```text
请先完整读取根目录 AGENTS.md 和 maintenance/README.zh-CN.md。这次任务是周期整理，遵守内容保护、审计流程、恢复和授权规则。

先只审计，不要修改记忆文档。如果这个私人副本还没有 `maintenance/baseline.json`，先运行一次 `node maintenance/.system/audit.mjs init`。然后运行 `node maintenance/.system/audit.mjs status` 和 `node maintenance/.system/audit.mjs validate`。有未完成 run 时完整读取 `maintenance/run/state.json`，按实际状态和 `next_action` 恢复；等待决定或执行时读取当前正式提议，不沿用历史批准。重新审计按协议使用 `refresh`。没有 run 时默认审计已变化文档，也可明确选择：

- 指定文档：重复使用 `--path`，或使用 `--paths-file`；需要预览依赖时先运行 `scope`；
- 已变化文档：不带 mode 运行 `start`；
- 全部文档：只有我明确要求时才运行 `start --mode full`，不因策略变化自动扩大范围。

完整读取每个目标及系统列出的必要只读依赖。不要把依赖自动变成写入目标，也不要把局部审计冒充全仓审计完成。

重点检查并提出方案：
1. fact、feeling 和 agent 内容是否符合 AGENTS.md 的归档边界，是否存在完整事件重复复述。
2. 在本轮范围内评估是否按独立事件或阶段拆分，或将分散的同一事件合并；不按篇幅机械处理。建议须原文保留全部记忆，说明内容去向、fact/feeling 对应关系、索引链接调整及回滚方式。
3. 两个 index、总时间线和事件内时间线是否符合排序规则，“最近更新”是否滞后。
4. current、overview、人物卡和主题索引是否仍履行路由与派生职责，是否保存了重复或唯一细节。
5. inbox 和 session 是否仍符合各自职责。
6. 链接、纯文本路径、文件名、日期精度和 UTF-8 是否一致。文件创建后优先保持路径稳定；只有文件名明显错误、重复或不利检索时才提出重命名方案，并在确认后同步所有引用。

审计阶段只写 maintenance/。用 `checkpoint` 保存已完成或部分完成的单元，通过 `publish --file <提议草稿.json>` 生成正式提议，不手写正式提议。默认人类视图必须先显示操作索引，再只展开真正的建议；每项显示精确的修改前、修改后和少量上下文，不要铺开所有已审计文档全文。

允许我通过 `revise` 新增、删除、替换操作或更换目标。只有我明确给出提议编号、版本和操作编号后，才能执行 `decision` 或 `apply`。只有 `apply` 可以修改记忆文档；如果目标、必要依赖或语义策略发生漂移，必须在任何写入前停止整批操作。完成后只汇报实际成功的写入，任何失败或不确定都要明确指出。准确命令和 JSON 格式见 `maintenance/README.zh-CN.md`。
```

## 阶段性摘要瘦身提示词

适合：`summary/current.md` 逐渐变成长篇近期记录，导致新对话启动上下文过大，或者未来 agent 容易被已经过期的近期细节带偏时使用。

不适合：不用于重建总时间线、新建人物卡、调整底层事件结构、全面整理其他摘要文件，或评估个人 review 等新结构。

```text
请先完整读取当前仓库根目录的 AGENTS.md。本次任务是“summary/current.md 阶段性瘦身”，不是完整周期整理，也不是普通聊天。

本轮只读，不得创建、修改、移动、重命名、删除或格式化任何文件。仅提交 `summary/current.md` 瘦身提案，列明具体操作、信息承接位置、风险和预计结果，随后停止。后续只执行我明确批准的编号、文件和操作，未批准的修改不得顺带处理。

本次唯一主要目标是把 current 从近期事件流水和分析汇总恢复为“当前状态快照”，从而显著减少新对话的启动上下文。不得为了达到固定字数或缩减比例而损失信息。

第一阶段只读审计：
1. 完整读取 summary/current.md，统计字符数、行数、条目数和各部分占用。
2. 读取 `summary/overview.md`、`fact/index.md`、`feeling/index.md`、`summary/people.md` 和 `summary/topics.md` 作为路由参考。
3. 对 current 中每条候选内容，只按需要读取直接相关的少量 fact、feeling、人物卡或 session，核验底层是否已经承接；不要默认读取全部底层记忆。
4. 无法确认底层是否承接时继续保留并标为待核验，不得仅凭摘要推断或直接删除。

一条内容只有符合至少一种情况时才继续留在 current：
- 关系、事件或目标仍在进行；
- 存在明确临近节点；
- 尚未解决的问题仍在影响近期决定或情绪；
- 近期反复出现，并且很可能继续成为后续对话入口。

仅仅最近谈过、曾经很强烈或具有长期意义，不足以留在 current。

每条活跃主线通常只保留：
- 当前结论或状态；
- 尚未解决的核心问题、使用者已经作出的明确决定或下一节点；
- 对应的 fact、feeling 或人物入口。

不保留状态形成过程的逐日更新、完整事件复述、重复背景和长篇分析。使用者明确表达且仍有效的需要、愿望和决定可以保留；agent 提出的建议、提醒和分析，除非后来被使用者明确采纳，不作为使用者当前状态保留。

从 current 移除的内容不自动迁入 timeline、overview、summary/people.md 或 topics。只有符合目标文件自身职责时才提出迁移；否则确认底层和 index 已有入口后，只把 current 中的派生副本列为移除候选。

如果某条个人内容只存在于 current，先判断它属于可确认事实、使用者明确情绪或愿望，还是 agent 分析。前两者提出底层承接方案；agent 分析不得新写入 session，旧版 session 中已有的分析保持原样。无法分类时继续保留并标记，不强行迁移。

默认写入候选只限 summary/current.md。overview、timeline、summary/people.md、topics、两个 index 和底层文件本轮只用于核验；如果 current 中的唯一信息必须先承接，或者瘦身会造成必要链接失效，将相关修改作为独立批次提出。不得借机重建 timeline、新建人物卡、调整事件结构或创建阶段性自我认识文件。

审计后先提交：
1. current 当前字符数、行数、条目数和主要膨胀来源；
2. 建议采用的新结构预览；
3. 保留、合并压缩、移除、待迁移和待核验的内容分类；
4. current 中的唯一信息及拟承接位置；
5. 每个拟修改位置、处理方式、理由、风险和可验证结果；
6. 预计瘦身后的字符数、条目数和缩减比例；
7. 需要我明确决定的问题。

确认执行后，只实施获批内容。完成后报告 current 的前后字符数、行数和条目数，检查 current 中的全部链接及获批跨文件修改所影响的链接，并确认未经批准的 fact、feeling、session、人物卡和其他摘要文件没有变化。任何失败或不确定都必须明确指出。
```
